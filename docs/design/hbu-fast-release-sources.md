## Deduplication, nightly resources, and design implications

**READ:** Selection deduplicates nodes with `dict.fromkeys`; each CLI invocation creates fresh timestamped logs and executes its selected nodes. **INFERENCE:** This runner provides invocation-local deduplication, not a shared successful-test cache across workers/batches. Loop deduplication of `(ticket, gate-reference)` concerns inbox work, not pytest results. The pre-commit tree stamp skips lint/skill work when present, not all tests. [test_policy.py:85](/Users/hanhnt2/Desktop/hblead-stream/hbu/src/hbu/harness/test_policy.py:85), [loop.py:1189](/Users/hanhnt2/Desktop/hblead-stream/hbu/src/hbu/harness/loop.py:1189), [pre-commit:21](/Users/hanhnt2/Desktop/hblead-stream/hbu/.githooks/pre-commit:21).

**READ:** Night eligibility is the 01:00 HCM start minute with continuous heartbeat; missed/sleep-delayed runs do not catch up during daytime. A date directory claims each slot once, and a shared nonblocking heavy lease prevents overlapping heavy runs. Snapshot pinning selects the then-current LIVE SHA. **INFERENCE:** HBU's nightly policy applies regardless of change size; it is not the user's requested major-change-only deep gate. Project Harness should preserve the corrected intent: release each small change quickly within a resource budget, with deeper validation for larger/high-impact changes. HBU batching and nightly aggregation are references, not evidence that this distinction already exists.
