# Paseo 0.13.0-beta.1 runtime delta — round 7

2026-10-23. **Changed/Unchanged** describe inspected contracts/source; **Unverified** means no integration proof. Baseline: `cafe4b01c8522ff39560241c5deb01427dc8dc5b` (0.12.0); beta: **`3fa625701eae6b3a07ccae18299200b1a7cf2776`**. Official client/plugin/protocol/server/CLI npm metadata agrees on that beta gitHead. Downloaded published declarations/JavaScript corroborate the pinned source; relevant files were compared directly across both commits. All Paseo source/documentation links below pin the beta. [^packages]

Read Matt’s research skill, technical-design-grill and facts r1–r4. Old facts remain historical. Only this report was saved; no live APIs, tests, installs, restarts, private configuration/credentials/transcripts, HBU reads or delegation.

## 1. Startup, authority and SDK access

**Unchanged:** server contracts, plugin-process and runtime are byte-identical. Setup still receives registrations, no SDK accessor/MCP registration/start-ready hook. The internally connected SDK reaches invoked RPC/hooks; ordinary RPC context remains only `{paseo}`, without authenticated caller principal/Session/generation or cancellation signal. Plugin RPC/lifecycle/catalog still require `daemon.manage`; schedule RPC requires `automation.manage`. T03’s explicit startup connection and own HTTP MCP/scoped tokens remain accepted. [^startup][^permissions]

**Changed opportunity:** high-level `PaseoApi.hosts` adds discovery/management and destination-scoped APIs; handles gain `address={serverId,agentId}`. The new public `@getpaseo/client/node` export supplies `createHostClient(connection,config): DaemonClient` and socket/SSH/relay transport helpers. Its published return type includes existing schedule, plugin lifecycle and RPC methods. Therefore revisit the blanket assumption “these methods require an internal import.” This exposed factory route is real; its suitability/stability as a plugin integration remains **unverified**, and `PaseoApi` itself still has no schedule/plugin-management methods. No host manager or transport replacement is selected. [^sdk][^node]

**Changed:** lower-level `sessionPermissions` is sent in hello and intersects admitted permissions, including reauthorization; high-level `PaseoClientConfig` does not expose it. This offers a connection ceiling, not new credentials, per-agent scope or caller attestation. Submitted requests interrupted by connection loss can now reject with `outcome:"unknown"` and destination server ID; reconcile before retrying. [^ceiling][^connection]

**Changed API compatibility:** lower-level agent creation now rejects legacy `git/worktreeName` placement despite lingering high-level options; message submission may return `deliveryStatus:"queued"`. Revisit old create/send fixtures against workspace-first placement and acceptance/delivery boundaries. This report does not re-audit full dispatch/tool-policy behavior. [^dispatch]

**Changed conflict:** `agent.turn_ended.timeline` remains declared but is deprecated and **always empty** in published server code, for completed/failed/canceled outcomes. Revisit any result/evaluator/reconciliation path consuming that payload. The declaration recommends on-demand timeline fetching; a tail of 20 items is not guaranteed complete Turn evidence. Hooks still provide no durable replay. [^hooks]

**Unchanged:** HTTP/SSE MCP carries literal string headers, without secret references; Claude forwards headers and Codex maps `http_headers`. Serialization still retains MCP configuration in native JSON. No new transport registration or principal propagation removes T03’s credential-custody/reconnect obligations. [^mcp]

## 2. Native scheduling and heartbeats

**Unchanged:** schedule types/RPC schemas, service/store/cron and relevant CLI scheduling/heartbeat implementations are byte-identical. Stored targets remain existing-agent/new-agent; no public code/workflow callback target. Advertised cadence remains cron/timezone, with internal compatibility `everyMs`; no at-instant/once contract. `maxRuns=1` and immediate run-once remain distinct. CLI/MCP schedules remain new-agent-only; CLI heartbeat create/update/delete is caller-bound, while MCP exposes heartbeat create/delete with ownership checks, without heartbeat inspect/logs/pause/resume. The Node factory changes accessibility, not these contracts. [^schedule][^schedule-access]

**Unchanged policy/durability limits:** native JSON history, serialized claiming/cursor advancement and per-schedule single-flight exist. There is no configuration CAS, acknowledged Work delivery/replay, configurable bounded catch-up/overlap/retry, global admission or logical-owner rebinding. Restart fails interrupted runs and advances overdue cursors; pause clears future cadence without canceling current work, while manual run-once may run paused schedules. T05’s one-owner/native-when-sufficient exception remains accepted. Newly expanded beta docs describe `archiveOnFinish`; source comparison shows this was already present, not a new scheduling capability. [^schedule][^schedule-doc]

## 3. Installation, reload, settings and UI identity

**Unchanged:** directory/managed acquisition, service, preparation, settings, subprocess and catalog-sync code are byte-identical. Directory installation records a host path; explicit reload stops/recompiles/restarts it, with no source watcher or manifest build on directory reload. Managed acquisition/update runs builds; failed candidate startup attempts previous-runtime restoration, and successful update removes previous managed source. Reload retains ID/settings; removal deletes settings, and settings migrations can persist during reads. These facts preserve T07’s prepared stable-ID/path publication with data/credentials/recovery outside replaced source. No atomic filesystem/native/schema transaction is supplied. [^deployment][^settings]

**Changed:** compiler adds SVG-as-text loading. Published client declarations add file panels, i18n and broader icons; UI imports consolidate under `/client/ui`, with deprecated `/client/react-native` alias. `useRevealedText` migration requires `StreamedText`; settings headings use `SettingsSection`. Revisit imported UI contracts and asset preparation, without treating additions as required Harness architecture. [^ui]

**Unchanged attestation gap:** runtime catalog still contains only ID/client bundle/requirements. Catalog notifications force replacement of that ID; reevaluation/disposal remains client-local, now also managing translations. No loaded backend digest/generation, whole-plugin identity or rendered-client acknowledgment appears. Server “running” and application metadata cannot establish complete activation. [^identity]

## 4. Runtime compatibility and remaining probes

**Changed:** plugin peers pin client/protocol exactly to beta; React broadens to `>=19.1.0 <20`. **Unchanged:** all five packages omit engines; pinned SDK docs require Node 22+. Compiler `node20` targets syntax; subprocess fork inherits daemon executable. Source still pins Electron 44.2.0. Read-only local public metadata shows app plus five bundled packages at beta and Electron framework 44.2.0; no executable/module probe was run. Actual plugin/recovery `node:sqlite` availability remains **unverified**. Prior Node observations do not establish current loaded runtime; version-specific SQLite APIs and synchronous blocking still need bounds. [^packages][^runtime][^sqlite]

Revisit package pins, runtime floors and manifest ranges: the unchanged requirements checker also accepts the prerelease’s stable core (`0.13.0`), so admission is not beta compatibility proof. CLI recovery remains independent of plugin RPC, but daemon/authentication/lifecycle availability and recovery executable/schema compatibility remain unproved. T03/T05/T07 and V1 stay intact. [^requirements][^recovery]

**Bounded contract probes, proposed only:** (1) disposable beta host: exact public Node-factory imports/bundling, explicit startup connection, permission ceilings and denied RPC; (2) one Session per provider: scoped HTTP authentication, redaction, endpoint reload/rebinding; (3) two schedules: heartbeat control/history, pause/manual-run races, crash around claim/delivery, timezone/downtime boundaries; (4) same-ID directory reload: candidate/backend/client/assets identity, settings continuity, offline-client refresh and lost reply; (5) isolated owner/recovery processes: runtime/SQLite exports, locking/transactions/migration/backup, stale-writer fencing, bounded daemon-unavailable/stuck-reload recovery. No live capability, architecture choice or V1 pass follows.
