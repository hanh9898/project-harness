## Targeted checks for additional material choices

**Common versus project updates.** Fact: A05 Q1 selects a source fork distinguishing common/project assets, rather than a separately released core dependency. Outbound contributions extract reusable code/tests/fixtures without private data; local activation never waits for upstream (`architecture.md:7,61`; `scope-80-20.md:74–78`). Missing: an explicit inbound base-update discovery/selection cadence and merge-conflict walkthrough. **Inference:** a selected upstream patch applied locally remains a candidate subject to existing checks, authority and project constraints. This does not authorize automatic imports or overwriting customizations. Merge tooling/layout is engineering; automatic discovery would be an additional product behavior if requested, not an established requirement silently needing approval.

**Bootstrap/evolution evaluators.** Readiness, operational verification and improvement evaluation already have different contracts (`../../GLOSSARY.md:199–217`; `first-run-ux.md:53–61`). A10 ships fixtures, not universal readiness. For evolution, representative/regression cases and sufficiently compatible Baseline/Candidate evidence are required for improvement claims; insufficient support remains Inconclusive (`release-policy.md:84–88`; `../domain/analytics/GLOSSARY.md:27–66`). Missing graders, datasets, thresholds and calibration are concrete engineering/project-policy work. Sources do not mandate an independent evaluator model, a five-role pipeline or baseline comparison for every patch; introducing any would need a proposed trade-off, not inference from “Verify.”

**Management visibility.** Existing requirements cover blockers, desired/observed state, revisions, native-session links, evidence and release/recovery guidance (`first-run-ux.md:67–88`; M:165,185; `../ui/GLOSSARY.md:34–72,129–207`). Knowledge explicitly does not require a CRUD UI (M:382). Missing: a complete cross-asset walkthrough showing installed/bound/selected/checked/active states for starter instructions, methods, evaluators and recovery artifacts. **Inference:** this is a documentation/projection gap; current sources neither promise exhaustive native-source visibility nor establish a new asset-management screen.

**Installable boundaries.** The fork contains source/operational assets; installed external Skills and native profiles remain prerequisites through their owners. Package manager, directories, loader registration and recovery-artifact distribution remain unselected (C:9,19,33,81–87; `paseo-boundary.md:13–23`). `release-execution.md:71–73,107` leaves compatible artifacts/executable updating incompletely integrated. These are tangible engineering/proof gaps; source presence cannot be reported as installed, runnable or verified. No contradictory accepted requirement establishes a second global installer or separate shared-core release.
